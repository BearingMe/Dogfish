## 1. Objectives & Non-Circular Validation Principles

The purpose of this strategy is to define how independently reconstructed models (primarily the Rust simulation crate under `reconstruction/`) are verified against the behavioral contracts established in [`docs/behavioral-contracts.md`](./behavioral-contracts.md).

### The Non-Circular Validation Invariant
- **Rule**: Expected test values must be independently derived from static Papyrus source code analysis, binary ESP record data, or audited contracts.
- **Prohibition**: Never assert tests against values generated by the implementation under test.
- **Anti-Pattern Avoidance**: Merely porting the historical Python verification scripts into Rust and asserting that the Rust function matches the Python function is circular. Tests must assert against explicit, hand-calculated test vectors grounded in primary evidence.

## 2. Seven-Tier Testing Architecture

Validation is partitioned across seven rigorous testing tiers:

```text
                                Tier 7: Integration Tests
                             (Skyrim Event Hook Vertical Slice)
                                             ▲
                                Tier 6: Differential Tests
                             (Reconstruction vs. Original Mod)
                                             ▲
                                Tier 5: Persistence Tests
                             (State Serialization / Round-Trip)
                                             ▲
                                Tier 4: Scenario Tests
                             (Cross-System Multi-Day Loops)
                                             ▲
                                Tier 3: Numerical Tests
                             (Hand-Derived Mathematical Math)
                                             ▲
                             Tier 2: State Transition Tests
                             (Domain State Machine Mutations)
                                             ▲
                                Tier 1: Contract Tests
                             (Preconditions, Types, Invariants)
```

### 2.1 Tier 1: Contract Tests
- **Objective**: Assert that functions reject invalid inputs and preserve domain invariants.
- **Scope**:
  - `HoldingId` bounds checking (0..14 allowed; 15+ rejected).
  - Treasury balances cannot be negative.
  - Army division indices clamped to 0..9 (`MaxArmies = 10`).
  - Division recruitment rejects zero or negative counts.

### 2.2 Tier 2: State Transition Tests
- **Objective**: Assert that domain entities transition through states strictly according to audited rules.
- **Scope**:
  - *Territory*: Unowned &rarr; Outpost &rarr; Staging Camp &rarr; Conquered Hold.
  - *Diplomacy*: Neutral &rarr; War &harr; Truce &rarr; Defeated.
  - *Progression*: Outlaw Rebel &rarr; Hold Conqueror &rarr; The Moot &rarr; High Monarch.
  - *Invalid Transitions*: Verifying that an army cannot invade a non-adjacent hold (`HoldsNotLinked`).

### 2.3 Tier 3: Numerical Equivalence Tests
- **Objective**: Assert mathematical simulation functions against independently hand-calculated test vectors.
- **Test Vectors**:
  - *Taxation*: $\text{Tax}(50, 2, \text{Major}) = 500(50) + 250(50)(2) = 50,000 \text{ gold}$.
  - *Taxation (Minor)*: $\text{Tax}(30, 1, \text{Minor}) = 300(30) + 150(30)(1) = 13,500 \text{ gold}$.
  - *Conscription*: $\text{Conscript}(11, 0.10) = \lceil 1.1 \rceil = 2 \text{ recruits}$.
  - *Technology Cost (Tier 5)*: $5000 + 3(10000) = 35,000 \text{ gold}; \, 50 + 3(100) = 350 \text{ metal}$.
  - *Docks Production Bonus*: $\lfloor 0.3 \times 10 \times 4 \rfloor = 12 \text{ units}$.

### 2.4 Tier 4: Scenario Integration Tests
- **Objective**: Evaluate multi-day simulation loops combining economy, military upkeep, and hold loyalty.
- **Standard Scenarios**:
  - *Scenario A (Famine Cascade)*: Set food yield to negative; run 7 daily update ticks; assert that food reserves drain, citizen loyalty drops below 40, and `ProtestQuest` triggers.
  - *Scenario B (Economic Growth)*: Set facility levels to 4; assert that `MaxJobs` exceeds population and civilian immigration occurs on 24h ticks.
  - *Scenario C (Bounty Detachment Combat)*: Execute 1,000 simulated bounty rolls; assert that victory frequency converges to $\text{Troops} / \text{Certain}$ within statistical tolerance.

### 2.5 Tier 5: Persistence Tests (Serialization Round-Trip)
- **Objective**: Assert that the entire domain state model survives serialization without data loss or corruption.
- **Protocol**:
  1. Initialize complex scenario (3 holds, 2 armies, active war, 50k gold).
  2. Serialize model to JSON / binary buffer.
  3. Drop in-memory instance.
  4. Deserialize model into fresh instance.
  5. Assert bit-for-bit or structural equality across all holdings, divisions, and globals.

### 2.6 Tier 6: Differential Comparisons
- **Objective**: Compare outputs of the standalone Rust simulation against documented behaviors of the original mod.
- **Scenarios**:
  - Compare casualty outcomes against `cs_bountyscript.psc`.
  - Compare The Moot voting tallies against `cs_meetingscript.psc`.
  - Classify discrepancies according to the 6-tier fidelity scale.

### 2.7 Tier 7: In-Game Integration Tests (M60)
- **Objective**: Validate the engine adapter bridge in an actual Skyrim Special Edition runtime session.
- **Scope**: Single-location claim experiment; asserts that a Skyrim event dispatches to the adapter and updates the model.

## 3. Six-Tier Fidelity Classification System

When assessing reconstructed systems, agents must use the following standard classifications:

| Classification | Definition | Evaluation Criteria |
| :--- | :--- | :--- |
| **`EXACT`** | Identical mathematical or behavioral equivalence demonstrated. | Test vectors match Papyrus code exactly; zero variance in outputs under equivalent inputs. |
| **`COMPATIBLE`** | Equivalent observable behavior with acceptable internal design differences. | Idiomatic Rust structs produce identical game-visible state mutations without duplicating Papyrus proxy containers. |
| **`APPROXIMATE`** | Core behavior reproduced, but documented minor differences remain. | Model handles general warfare and economy, but specific micro-heuristics (e.g. AI general battle math) use simplified equations. |
| **`INCOMPLETE`** | Subsystem is missing significant features or contains stubs. | Features marked as stubs (e.g., civil tech perks, v0.4.0 loyalty mutiny). |
| **`UNKNOWN`** | Insufficient primary evidence to evaluate fidelity. | Mechanics that cannot be recovered from bytecode or records. |
| **`CONTRADICTED`** | Reconstructed model conflicts with verified primary evidence. | Model produces an outcome that contradicts established script logic. |

## 4. Separation of Automated vs. Human-Dependent Testing

| Dimension | Automated Simulation Tests (Rust / Python) | Empirical Human Playtesting (Skyrim Runtime) |
| :--- | :--- | :--- |
| **Execution Tool** | `cargo test`, `python -I -m unittest` | Skyrim SE/AE game client, Mod Organizer 2 |
| **Location in Repo** | `reconstruction/src/`, `tests/` | `research/playtesting/test-plan.md` |
| **Dependencies** | Standard compiler, zero game engine | Skyrim SE runtime, SKSE64, graphics hardware |
| **Determinism** | 100% Deterministic (fixed PRNG seeds) | Subject to Havok physics, framerates, user input |
| **Result Storage** | Automated terminal test reports | Markdown test logs in `research/playtesting/` |
| **Status in Repo** | Passing 16/16 unit tests | Codified test plan; results pending human playtest |
